# Playbook: Android-приложения с LLM и офлайн-OCR

Сводный опыт двух проектов: Chaquopy+WebView+ONNX (исходный playbook,
13 итераций) и OfflineRef (Kotlin+llama.cpp+RAG+OCR, ~30 итераций).
Каждое правило оплачено часами отладки в поле. Порядок разделов =
порядок проверки при любом баге: сначала то, что молчит (конфигурация),
потом зависимости, потом код, потом железо.

---

## 0. Железные правила процесса

1. **Пуш обязан быть подтверждён.** После `git push` - `git ls-remote origin main`;
   при работе через REST API - читать HEAD через API. Несвязанные истории ->
   push молча отклоняется: `git fetch && git reset --hard origin/main` перед работой.
2. **Репозиторий - единственный источник истины.** Sandbox теряет /tmp,
   ядро умирает между сообщениями. Пуш рано, коммить часто. Восстановление
   дерева: git trees API (recursive) -> скачать каждый blob -> собрать заново.
3. **Git-протокол может быть заблокирован, а REST API - нет** (connection reset
   на git push, api.github.com жив). Пуш через Contents API (GET sha -> PUT
   base64). Побочка: N файлов = N коммитов = N CI-запусков, это нормально.
4. **Один файл = одна версия.** Никогда не перезаписывай APK одним именем;
   `sha256sum` каждую сборку, таблица версий. "Размер тот же" != "файл тот же".
5. **Каждый патч подтверждай применением.** replace() без assert молча
   ничего не делает при неточном паттерне - дважды чуть не ушли полупатченные
   файлы в CI. Читай файл обратно, проверяй маркеры.
6. **CI - единственный честный источник APK.** Артефакты кладутся на blob-
   хранилище, которое умирает чаще, чем API. Запасной канал: CI зеркалирует
   APK в служебную ветку (`apk`), забирать через raw.githubusercontent.com.
   ВНИМАНИЕ: mirror-шаг НЕ чистит ветку (git rm -rf молча снёс чужой файл).
7. **Бисекция на каждом нативном шаге:** сначала скелет "B1 OK", потом слои
   по одному (JNI-заглушка -> полный движок). Падение локализуется одной сборкой.

## 1. Конфигурация: то, что молчит

1. **Kotlin-плагин в ОБОИХ build.gradle** (`org.jetbrains.kotlin.android`) +
   compileOptions JVM 17. Без него AGP молча игнорирует .kt: сборка успешна,
   класса в dex нет, приложение падает мгновенно. Проверка после сборки:
   распарсить dex, найти MainActivity.
2. **buildConfig выключен по умолчанию в AGP 8** - `BuildConfig.VERSION_NAME`
   без `buildFeatures { buildConfig true }` не существует.
3. **ГЛАВНЫЙ БАГ LLM-ПРОЕКТА: debug-сборка = CMAKE_BUILD_TYPE=Debug, NDK для
   Debug ставит -O0.** Весь ggml/llama.cpp считает в 20-50 раз медленнее:
   "зависание" первого decode при любой модели/потоках/версиях. Лечение в
   CMakeLists ДО FetchContent:
   `set(CMAKE_CXX_FLAGS_DEBUG "${CMAKE_CXX_FLAGS_DEBUG} -O3")` (и для C).
4. **16KB-страницы памяти (Android 15/16):** NDK 27+, onnxruntime >= 1.20,
   свежие нативные зависимости. Иначе процесс умирает на dlopen до кадра.
5. `android:extractNativeLibs="true"`, `abiFilters arm64-v8a`, minSdk 26.
6. **SQLite FTS5 на устройстве НЕ гарантирован** ("no such module: fts5"
   на части прошивок; поведение по устройствам разное). Не полагаться:
   замена - скан по подстрокам + подсчёт слов + top-k (для сотен фрагментов
   миллисекунды), try/catch -> fallback.

## 2. Android: UI и сеть

1. **CalledFromWrongThreadException убивает процесс с задержкой ~1 с.**
   addView/setText с чужого потока падают на следующей отрисовке. UI-утилиты
   (лог-бабблы, статусы) прыгают на UI-поток внутри себя - тогда все
   вызывающие защищены.
2. **HttpURLConnection + HTTP 404 = FileNotFoundException с URL в message.**
   Читай responseCode ЯВНО до getInputStream, клади код в текст исключения.
3. **SQLiteOpenHelper: context сохрани в поле класса**, super его не держит.
4. Аварийный экран с traceback + ACTION_SEND (один тап - лог у разработчика).
5. Пошаговый статус запуска: нативный краш ЗАМОРАЖИВАЕТ последний текст -
   локализация без logcat (главное достижение исходного проекта, сохранено).

## 4. LLM на устройстве

### Классификация железа - до выбора модели
- Средний класс (Dimensity 7200/7300, Snapdragon 7xx): модели <=3-4B.
  7B - флагманы; рабочий 7B на среднем классе ~2-2.5 ток/с (акад. замеры).
- Эталон: на Nothing Phone (2a) Phi-3-mini 3.8B Q4_K_M - первый токен 3.9 с.

### Замеры (Nothing Phone 2a, Qwen2.5-3B Q4_K_M, -O3)
- Промпт ~160 мс/токен (batch, 4 потока). Генерация 230-330 мс/токен (2 потока);
  4 потока генерацию НЕ ускоряют (упор в память), но греют.
- llama.cpp: n_threads=2 (генерация), n_threads_batch=4 (промпт). Раздельно.
- Бюджет 60 с: промпт <=300 токенов + ответ <=150-200. Русский ~2.5 знака/токен:
  RAG-контекст <=1500-1800 знаков (1-2 чанка по 550 знаков).

### llama.cpp
- Пиновать GIT_TAG через FetchContent. v0.5.0 (новый memory-sched) на Android
  зависала в первом decode 200+ с даже холодной и на 1 потоке; b4353 (обкатан
  в llama.rn/ChatterUI) - рабочая. Новое != обкатанное.
- API меняется между версиями: chat_apply_template (с model / без), vocab-API
  появился после b4353, llama_free_model vs llama_model_free. Сверяй сигнатуры
  с версией, не с памятью.
- Сэмплирование - только штатный sampler-chain (penalties 1.10 + temp + dist).
  Ручной softmax давал заикание первого слова ("ПрПрП") даже при temp 0.1.
- UB: токен для следующего decode живёт ВНЕ тела цикла (batch.token = &last).
  При -O0 работает, при -O3 - непредсказуемо.
- use_mmap=false для офлайна: файл, вытесненный из page cache, превращает
  первый decode в бурю page faults. Чтение в ОЗУ при загрузке 3-5 с.
- Chat template только через llama_chat_apply_template (метаданные GGUF).
- Модель: sha256 эталон в коде; скачивание с докачкой Range, атомарный
  rename .part; пустой эталон -> приложение показывает фактический хэш.

### База знаний
- Чанки ~550 знаков, перекрытие последним абзацем; chunks: ordinal, page_no,
  img_path. Структурированные данные (дозы, контакты) - отдельными таблицами
  с точным lookup, не через RAG.
- Миграции БД: ALTER TABLE ADD COLUMN с try/catch каждый (idempotent).

## 5. OCR и сканированные документы

1. **ML Kit Text Recognition НЕ поддерживает кириллицу** (латиница, китайский,
   японский, корейский, деванагари). Проверяй языки ДО интеграции.
2. **On-device OCR русского = tesseract.** `com.rmtheis:tess-two:9.1.0`
   (mavenCentral, Tesseract 4.0.0, пакет com.google.tesseract.android).
   Tesseract4Android - тот же API, но через jitpack (раннеру не отдал).
3. **PdfBox берёт только текстовый слой** - скан даёт пустоту. Fallback:
   android.graphics.pdf.PdfRenderer -> Bitmap -> tesseract. Страницы рендерить
   сразу в JPEG (quality ~60, ширина ~1100px): и OCR, и "📷 стр. N" в UI.
4. **rus.traineddata (3.8 МБ) в git не храним** - CI кладёт в assets перед
   сборкой из tessdata_fast. Sandbox-канал умирает на файлах >1.7 МБ
   (raw игнорирует Range, зеркала rate-limit): обход - CI коммитит файл в
   служебную ветку, sandbox забирает через Contents API (api.github.com).
5. **Mirror-шаг CI не чистит служебную ветку** - git rm -rf снёс чужой файл.
6. Sandbox: tesseract часто предустановлен БЕЗ данных; "Error opening data
   file" при живом --list-langs = обрезанный файл. Проверяй размер HEAD-ом,
   не верь rc curl.

## 6. Культура диагностики

1. Нативный лог-мост в UI: llama_log_set -> JNI -> серая строка в чате.
2. Фазовые маркеры "phase: ..." из своего кода в тот же канал (с таймингом).
3. Секундомер до первого токена (тикер 1 с): "зависло" vs "медленно".
4. Стриминг токенов через JNI-колбэк - и UX, и измеритель скорости.
5. Бенчмарки: НЕ зови System.nanoTime() в цикле (меряешь syscall: 5 млн
   итераций/с вместо ~1 млрд и ложный вывод "CPU зажат"). Проверяй раз в
   миллион итераций.
6. Одна гипотеза = одна сборка. Порядок: конфигурация -> версия движка ->
   размер модели -> флаги -> железо. Решения - по цифрам decode N done, X ms.
7. Диагностика БД при старте (путь/размер/счётчики) + автобэкап JSON после
   каждого импорта: базу один раз молча снесло, археология не восстановила -
   а бэкап восстановил бы за минуту.

## 9. Постскриптум: что НЕ понадобилось

1. **16KB-страницы на Nothing Phone 2a - не проблема.** tess-two (сборка 2021)
   загружается и работает на Android 16: доказательство - ошибка пользователя
   "Unsupported pixel format" возникла ВНУТРИ setImage(), т.е. библиотека
   дошла до работы. Ветка собственной сборки tesseract (NDK 27) отложена как
   ненужная: гипотеза опровергнута эмпирически, не строим спекулятивное
   решение. Урок: риск "старые .so + 16KB" проверяется дешёвым тестом на
   устройстве до инвестиций в пересборку.
2. Собственная кросс-сборка tesseract+leptonica под Android (FetchContent,
   NDK 27) - проходима, но дорога: try_compile-фикс, обход find_package,
   шимы CpuFeatures, libtesseract vs tesseract-CLI, include-директории
   сгенерированных заголовков. Если когда-нибудь понадобится - ветка
   tess-ndk27 в репозитории содержит все 8 фиксов.

*Два проекта, ~70 CI-итераций. Главный урок: когда "всё медленно и никто не
знает почему" - проверяй флаги компиляции раньше, чем железо, а молчащие
зависимости (плагины, модули SQLite, CDN библиотек) - раньше, чем код.*

## 8. Дополнение: офлайн-библиотека с иллюстрациями (опыт OfflineRef 0.18)

1. **Встроенная база в APK = assets-zip + версионирование.** assets/kb_base.zip
   (CI кладёт из служебной ветки), предзагрузка при первом запуске. Поле
   asset_version в prefs: смена версии = clearAll + пересоздание, иначе фиксы
   чанкования не доходят до существующих установок. Без версионирования
   предзагрузка дублирует документы.
2. **Contents API не пишет файлы >~50 МБ** - нарезка на 4 МБ-части в служебную
   ветку (bp.partNN), CI склеивает cat-ом. Чтение через Accept: raw работает
   для любых размеров.
3. **tess-two setImage() требует ARGB_8888** - Bitmap RGB_565 падает с
   "Unsupported pixel format". Рендер PdfRenderer сразу в ARGB_8888.
4. **SAF с EXTRA_MIME_TYPES фильтрует жёстко**: забыл application/pdf в списке -
   PDF в файловом picker просто не выбирается. Проверяй список типов против
   всех форматов, которые реально импортируешь.
5. **Привязка фрагментов к страницам OCR-книг**: OCR-текст с метками
   "[стр. N]" в начале секции + страницы JPEG в assets; предзагрузка парсит
   метки и ставит chunks.page_no/img_path. Кнопка "📷 стр. N" в ответе.
6. **Диагностика через тот же UI-канал** (KbDb.lastDiag -> logBubble): импорт
   пишет "tess init ok/FAIL", "OCR вернул пустоту", итоговые счётчики - полевой
   пользователь присылает скрин, разработчик видит точку отказа без adb.
7. **Sandbox-ядро умирает регулярно, /tmp стирается** - все долгоживущие
   артефакты (traineddata, промежуточные результаты) хранить в персистентном
   output/, OCR-прогон делать докачиваемым (skip if exists).
8. **Дубли предзагрузки при миграции**: guard "hasDocuments && version ==
   current -> return" плюс "version != current -> clearAll перед импортом".
   Обе ветки обязательны.
