# Playbook v2: LLM-приложения на Android с нуля до работающего

Собрано из реального проекта OfflineRef: офлайн-справочник (LLM на устройстве,
база знаний, RAG) для Nothing Phone 2a / Dimensity 7200 / Android 16.
Дополняет исходный playbook (Chaquopy/WebView), не заменяет его.
Каждое правило ниже — оплачено часами отладки в поле, без компьютера, по
скриншотам пользователя. Порядок разделов = порядок проверки при любом баге.

---

## 1. Процесс: правила, которые важнее кода

1. **Репозиторий — единственный источник истины.** Sandbox теряет `/tmp`,
   ядро умирает между сообщениями, локальные копии исчезают. Пуш рано,
   коммить часто, работай из состояния репозитория. Восстановление:
   git trees API (recursive) -> скачать каждый blob -> собрать дерево.
2. **Git-протокол может быть заблокирован, а REST API — нет.** Если
   `git push` падает (connection reset), пушь через Contents API
   (GET sha -> PUT с base64). Побочка: N файлов = N коммитов = N запусков
   CI, это нормально. Подтверждать пуш = читать HEAD через API.
3. **Всегда подтверждай, что патч ПРИМЕНИЛСЯ.** `replace()` без assert
   молча ничего не делает при неточном паттерне — дважды чуть не ушли
   в CI полупатченные файлы. После каждой правки: читай файл обратно и
   проверяй маркеры.
4. **Артефакты CI могут быть недостижимы.** Скачивание артефактов идёт
   на стороннее blob-хранилище; оно умирает чаще, чем api.github.com.
   Решение: CI сам зеркалирует APK в ветку `apk` (git push из workflow,
   permissions: contents: write), забирать через raw.githubusercontent.com
   — отдельный маршрут, обычно живой. Плюс это бэкап всех сборок.
   Большие файлы качаются Range-кусками (1-3 МБ за ячейку/шаг).
5. **APK: уникальные имена, sha256, фиксированный keystore** — из
   исходного playbook, без изменений. Дополнение: фиксированный keystore
   хранится в репозитории как base64 и декодируется build.gradle'ом
   при сборке — бинарник в git не нужен.
6. **Бисекция — на каждом нативном шаге.** Сначала JNI-мост-"заглушка"
   (проверка: .so грузится на устройстве), потом полноценный движок.
   Когда «всё падает без причин» — проверяй сначала то, что молчит:
   плагины, флаги, пуши, хэши.

## 2. Android/Kotlin: ловушки, каждая из которых стоила итерации

1. **ГЛАВНЫЙ БАГ ПРОЕКТА: AGP собирает debug-APK с CMAKE_BUILD_TYPE=Debug,
   а NDK для Debug ставит -O0 (без оптимизации).** Симптом: первый
   llama_decode «зависает» на 80-300+ секунд при ЛЮБОЙ модели, числе
   потоков, температуре и версии llama.cpp. Железо ни при чём.
   Лечение в CMakeLists.txt ДО описания таргетов:
   `set(CMAKE_CXX_FLAGS_DEBUG "${CMAKE_CXX_FLAGS_DEBUG} -O3")` (и C).
   Проверка: в логах устройства замеры должны соответствовать классу железа.
2. **buildConfig выключен по умолчанию в AGP 8.** `BuildConfig.VERSION_NAME`
   без `buildFeatures { buildConfig true }` = compile error. AGP молчит,
   только компилятор Kotlin ругается — ищи "Unresolved reference: BuildConfig".
3. **CalledFromWrongThreadException убивает процесс с задержкой ~1 с.**
   Любое `addView`/`setText` с не-UI потока падает не сразу, а на
   следующей отрисовке. Утилиты, пишущие в UI (лог-бабблы, статусы),
   обязаны сами прыгать на UI-поток внутри (runOnUiThread) — тогда
   все вызывающие защищены автоматически.
4. **HttpURLConnection + HTTP 404 = FileNotFoundException, у которого
   message — это URL.** Диагностика выглядит как "ошибка: <адрес>".
   Читай `responseCode` ЯВНО до getInputStream и клади код в исключение.
   Реальный кейс: файл переехал в репозитории (Xet), URL отдал 404.
5. **`SQLiteOpenHelper(context, ...)`: context надо сохранить в поле
   класса**, если он нужен методам (contentResolver). Конструктор
   отдаёт его в super и забывает.
6. **Устаревшие API подписи меняются между версиями llama.cpp** — см. раздел 3.

## 3. LLM на устройстве: цифры и правила

### 3.1. Классификация железа — до выбора модели
- Средний класс (Dimensity 7200/7300, Snapdragon 7xx): модели ≤3-4B.
  7B — только флагманы; на среднем классе даже РАБОЧИЙ 7B даёт ~2-2.5
  ток/с декодирования (академические замеры: SD870 — 2.5 ток/с для 7B Q4).
- Замеры Alibaba на Nothing Phone (2a): Phi-3-mini 3.8B Q4_K_M, первый
  токен 3.9 с (2 потока). Эталон для проверки своей сборки.

### 3.2. Наши замеры (Nothing Phone 2a, Qwen2.5-3B Q4_K_M, -O3)
- Загрузка модели (mmap off, чтение в ОЗУ): 3-5 с (тёплый кэш).
- Промпт: ~160 мс/токен (batch, 4 потока): 87 токенов ≈ 13.8-15.7 с.
- Генерация: ~230-330 мс/токен (2 потока), 4 потока НЕ ускоряют —
  упор в память, только греют.
- Вывод: llama.cpp позволяет разные потоки — `n_threads` (генерация) = 2,
  `n_threads_batch` (промпт) = 4. Именно так.
- Бюджет 60 с: промпт ≤300 токенов + ответ ≤150-200 токенов. Русский
  ~2.5 знака/токен: контекст RAG не больше ~1500-1800 знаков (1-2 чанка
  по 550 знаков). Это ограничение архитектуры, а не настройки.

### 3.3. llama.cpp
- **Пиновать версию через FetchContent с GIT_TAG.** v0.5.0 (свежая,
  новый memory-sched) на Android зависала в первом decode 200+ с — даже
  на холодном телефоне, на 1 потоке. Откат на b4353 (обкатанна в
  llama.rn/ChatterUI) решило. Новое ≠ обкатанное.
- **API меняется между версиями, сверяй сигнатуры:**
  - b4353: llama_chat_apply_template(model, tmpl, ...) — С model;
    v0.5.0: БЕЗ model. llama_tokenize(model,...); vocab-появился позже
    b4353. llama_free_model vs llama_model_free.
  - b4353 не знает vocab-API (llama_model_get_vocab, llama_n_vocab(vocab)).
- **Сэмплирование: только штатный sampler-chain**
  (llama_sampler_chain_init + penalties(64, 1.10, 0, 1.05) + temp + dist).
  Ручной argmax/softmax давал заикание первого слова ("ПрПрП", "Я ЯЯ")
  даже при temp 0.1. Штраф за повторы обязателен.
- **UB: токен, подаваемый на следующий decode, должен жить вне тела
  цикла.** `batch = llama_batch_get_one(&next, 1)`, где next — локальная
  переменная итерации = висячий указатель между итерациями. При -O0
  работает, при -O3 — непредсказуемо.
- **use_mmap = false для офлайн-приложений.** Файл, скачанный месяц назад,
  вытеснен из page cache — тогда первый decode = буря page faults
  (4 КБ случайные чтения с UFS). Чтение в ОЗУ при загрузке (линейное,
  3-5 с) делает поведение предсказуемым. На 12 ГБ ОЗУ — доступно.
- **Модель: sha256 эталон в коде**, считается на лету при скачивании,
  атомарное rename .part -> готовый файл, докачка Range'ами. Если эталон
  ещё не известен — приложение показывает фактический хэш, разработчик
  вписывает следующим коммитом.
- **Chat template — только через llama_chat_apply_template** (шаблон из
  метаданных GGUF, add_assistant=true), не руками.

### 3.4. База знаний / поиск
- **SQLite FTS5 на устройстве НЕ гарантирован** ("no such module: fts5"
  на Nothing/Android 16 — при этом создание таблицы когда-то проходило,
  запросы — падают; поведение по прошивкам разное). Не полагаться.
- Рабочая замена: скан чанков + подсчёт совпавших слов + top-k. Для базы
  в сотни-сотни фрагментов — миллисекунды. Оборачивать в try/catch ->
  пустой результат = fallback-режим, а не краш вопроса.
- Чанкование ~550 знаков, перекрытие последним абзацем. Ограничение
  под бюджет промпта (см. 3.2).
- Русская морфология: ни FTS, ни подстроки не склоняют. Это известный
  долг v2 — эмбеддинги (гибрид с подстроками).

## 4. Культура диагностики (главное достижение проекта)

1. **Нативный лог-мост в UI через JNI**: llama_log_set -> CallStaticVoidMethod
   -> серая мелкая строка в чате. Пользователь в тайге: ни adb, ни логов —
   а тут каждая фаза загрузки/генерации на экране.
2. **Фазовые маркеры "phase: ..."** из своего кода в тот же канал:
   backend init / load_model / new_context / template / tokenized /
   decode N begin+done (с таймингом!). Один запуск пользователя
   локализует зависание без единого вопроса.
3. **Секундомер до первого токена** (ticker на 1 с): отличает "зависло"
   от "медленно работает" без слов.
4. **Бенчмарки — правильно**: не зови System.nanoTime() в цикле — меряешь
   syscall (~5 млн итераций/с вместо ~1 млрд, ложный вывод "CPU зажат").
   Проверяй время раз в миллион итераций.
5. **Стриминг токенов через JNI-колбэк** — не только UX: скорость видна
   невооружённым глазом, токены/сек считаются по decode-таймингам.
6. **Одна гипотеза = одна сборка**, порядок проверки: конфигурация ->
   версия движка -> размер модели -> флаги -> железо. Каждый шаг
   фиксируй цифрами (decode N done, X ms), решения принимай по данным,
   не по ощущениям.
7. **Аварийный экран с кнопкой "отправить лог"** (ACTION_SEND) — из
   исходного playbook; дополнение: thread-safe реализация (п.2 раздела 2).

## 5. Чек-лист нового LLM-проекта

- [ ] Kotlin-плагин в обоих build.gradle, JVM 17, buildConfig true
- [ ] CMake: -O3 в Debug-флагах ДО FetchContent

- [ ] llama.cpp: пинованный обкатанный тег (b4353-class), sampler-chain,
      токен вне цикла, chat_apply_template, раздельные n_threads

- [ ] Модель-менеджер: докачка Range, атомарный rename, HTTP-коды явно
- [ ] Поиск по базе: без FTS5, try/catch -> fallback
- [ ] Лог-мост JNI + фазовые маркеры + секундомер + стриминг
- [ ] UI-утилиты потокобезопасны изнутри
- [ ] CI: dex-проверка, sha256, уникальные имена, keystore из base64,
      зеркалирование APK в ветку apk
- [ ] Скелет сначала "B1 OK", каждый слой отдельным шагом

## 6. Цифры для быстрой калибровки (Nothing Phone 2a)

| Параметр | Значение |
|---|---|
| Модель | Qwen2.5-3B-Instruct Q4_K_M (~1.9 ГБ) |
| Промпт 87-112 ток | 13.8-23.7 с (4 потока batch) |
| Генерация | 230-330 мс/ток (2 потока) |
| Ответ "привет" | 16-18 с total |
| Ответ факт-вопрос | 29-37 с total |
| RAG-ответ (2 чанка) | до ~60 с, контролируется |
| Загрузка модели в ОЗУ | 3-5 с (тёплый кэш) |
| Красные флаги | decode 0 > 60 с -> -O0 или 7B; генерация > 400 мс/ток -> троттлинг |

*Проект: OfflineRef. ~20 CI-итераций от "пустой репозиторий" до
офлайн-RAG-справочника. Главный урок: когда "всё медленно и никто не
знает почему" — проверяй флаги компиляции раньше, чем железо.*
